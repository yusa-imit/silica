# Silica — Architecture

## Concurrency Limitations (CRITICAL — Session 40 Finding)

**Silica v0.7.0 does NOT support concurrent connections.**

### Per-Connection Resource Isolation

Each `Database.open()` creates isolated instances:
1. **Buffer Pool** (engine.zig:743-746) — Separate in-memory page cache per connection
2. **WAL** (engine.zig:751-756) — **CRITICAL BUG**: Multiple Wal instances write to same file without synchronization!
3. **Transaction Manager** — Correctly shared via global registry

### Concurrency Bugs

1. **WAL Corruption**: Multiple connections write interleaved frames to `db-wal` → corrupt checksums, lost frames
2. **Stale Cache**: Connection A modifies page → Connection B serves old cached copy from its buffer pool
3. **Rollback Hazard**: Connection A's rollback truncates WAL, may discard Connection B's committed data

### Impact

- Jepsen-style concurrent tests fail with data loss (expected 1000, found 995)
- UPDATE/DELETE in concurrent transactions cause NoRows errors (issue #20)
- Multi-connection workloads are UNSAFE

### Fix Required (Milestone 26+)

1. **Shared Buffer Pool** with proper locking (like PostgreSQL's shared_buffers)
2. **Single WAL Manager** or serialized WAL writes
3. **Multi-version storage** for true MVCC

**Current Status**: Single-connection mode only. Multi-connection support deferred to Milestone 26.

## GIN Index Native Storage Wiring — Architect Design (Session 469, 2026-07-16)

**Problem**: `src/storage/gin_index.zig` (GIN posting-list struct: insert/delete/search, inline + posting-tree pages) and `src/storage/gist_index.zig` are fully implemented but **never invoked** anywhere outside their own files. `CREATE INDEX ... USING GIN` records `idx_type=.gin` in the catalog but the root page is initialized and used as a plain B+Tree page — DML (`insertIndexEntries`/`deleteIndexEntries`, engine.zig ~4923-5008) and scans (`IndexScanOp`, `BitmapIndexScanOp`, executor.zig ~8285/12263) all route `.gin`/`.gist` through `BTree.init(...).insert/delete/get`. Containment/full-text predicates (`@>`, `?`, `?|`, `?&`, `@@`, array `&&`) are only ever evaluated as per-row scalar checks during a full scan (`evalContainment`/`jsonContains`, executor.zig ~2260-2336) — never index-assisted. Confirmed via direct grep/read, not speculation (see [[next-priorities]]).

**Root blocker — row identity mismatch**: Silica is index-organized (rows live in a data B+Tree keyed by `row_key`, which is an 8-byte big-endian int for rowid tables but arbitrary bytes for PK tables). `gin_index.zig`'s posting lists store `ItemPointer{page_id, tuple_offset}` — a *physical* heap TID silica doesn't have. The existing `BitmapIndexScanOp`/`BitmapHeapScanOp` "TID" path is a known-broken placeholder (hashes row_key into a fake TID, ~8 tests skipped, **no MVCC visibility check** — do not build on it, violates rule 15).

**Resolution (Option A, adopted)**: restrict native GIN to rowid tables (row_key is exactly 8 bytes); pack the row_key bit-for-bit into the existing `ItemPointer` u64 field (ignore its page_id/offset semantics, treat as opaque 8-byte handle). Text/composite-PK tables keep the B+Tree fallback forever. This needs zero low-level page-format change to `gin_index.zig`.

**7-step phased plan** (each step TDD, green, B+Tree fallback intact until final cutover — gated behind a new `IndexInfo.gin_opclass` field that no existing catalog sets, so steps 1-6 are invisible to current behavior):

2. ✅ **DONE (session 474, commits 5b76b1c/816938e)** `gin_index.zig`: all three opclasses complete. `array_ops` (session 471) — `ArrayOpsOpClass` (gin_index.zig ~171-317, 20 tests ~1394-1770) implements compare/extractValue/extractQuery/consistent. Input wire format is a local, independent reimplementation (storage layer must not import sql layer) of the tag+payload scheme used by executor.zig's `serializeValue`/`deserializeValue` (0x00 null … 0x0C array … 0x10 tsquery) — `column_value`/`query_value` must be a 0x0C array; each element's raw tag+payload span becomes one GIN key. `compare()` is deliberately plain lexicographic byte comparison (not type-aware/numeric) since GIN's entry-tree only needs a consistent total order, not semantic magnitude ordering — this is the reusable pattern for the other opclasses. Known follow-ups (not blockers, tracked for a future test-quality/stabilization pass): (a) no recursion depth limit on nested-array (0x0C-in-0x0C) parsing in `valueSpanLen` — mirrors a pre-existing identical gap in executor.zig's `deserializeValue`; (b) test suite only exercises integer/text element types, not boolean/date/time/timestamp/interval/numeric/uuid/tsvector/tsquery/nested-array elements. `jsonb_ops` (session 472, commit 6a936ef) — `JsonbOpsOpClass` supports only `@>` (strategy 0) — `?`/`?|`/`?&` deliberately out of scope, need an `extractQuery` interface change to express cleanly. ## Index-Only Scan — Architect Design (Session 487, 2026-08-22)

**Problem**: `src/sql/index_entry.zig` (committed session 487, commit 9d7a358) is a storage-agnostic encode/decode wire format for covering-index B+Tree leaf entries, but nothing writes or reads it yet. Secondary index B+Tree leaf values are `row_key`-only (confirmed `engine.zig:5068-5069` `insertIndexEntries`), so `INCLUDE (...)` columns (fully parsed + catalog-persisted already: `ast.CreateIndexStmt.included_columns`, `catalog.IndexInfo.included_columns`) are currently decorative — a covering-index query still needs a heap fetch, defeating the point.

**Key finding — existing scaffolding is half-wired and currently a dead/broken no-op, not a blank slate**: `planner.zig:186` `PlanNode.Scan.index_only: bool` and `optimizer.zig:172-195` `optimizeScan` (calling `indexCoversColumns` at optimizer.zig:428-445) already exist and can set `index_only = true` — but (a) `scan.columns` fed into `indexCoversColumns` is always the *full table schema* (planner.zig:1040-1049), not query-referenced columns, so the check essentially never passes for a realistic partial-covering index, and (b) `engine.zig`'s `buildTableScan`/`tryBuildIndexScan` never read `scan.index_only` at all (zero hits outside planner/optimizer). 4 commented-out acceptance tests already exist at `executor.zig:18121-18260` specifying the intended end-to-end semantics — adapt, don't write from scratch.

**No B+Tree/page-format change needed** — unlike the GIN cutover, `BTree.insert(key, value)` already handles arbitrary-length values via the existing `overflow.zig` mechanism, so wider covering-index leaf values need no new storage capability.

**MVCC**: `DecodedIndexEntry.header` is the same `mvcc_mod.TupleHeader` type used everywhere; visibility check is exactly `mvcc_mod.isTupleVisibleWithTm(decoded.header, ctx.snapshot, ctx.current_xid, ctx.current_cid, ctx.tm)` — identical to `IndexScanOp.next()`'s existing call (executor.zig:8352). Every DML path writes the index entry's header from the *same* `TupleHeader` value used for the heap row in the same call, and every UPDATE unconditionally rewrites all secondary index entries (engine.zig:5921-5938) regardless of whether the indexed column changed — so covering entries can't go stale relative to the heap row.

**Backward compatibility gate**: new `IndexInfo.covering_storage: bool = false` catalog field (mirrors `gin_opclass`'s exact backward-compatible trailing-byte pattern, catalog.zig:380-381). Defaults `false` for every pre-existing serialized index row — **this flag, not `included_columns.len > 0`**, gates index-only scan selection. An old `INCLUDE`-clause index has non-empty `included_columns` already but row_key-only leaves; using column-presence as the trigger would misparse legacy leaves as covering entries. `optimizeScan` requires `idx.covering_storage == true` *and* the column-coverage check.

**Scope**: `covering_storage` only ever settable for `index_type == .btree` (composite index *keys* aren't even supported today — `IndexInfo` is single-column-key only, engine.zig ~8194-8196 only uses `ci.columns[0]`). `.hash`/`.gist`/`.gin` covering storage explicitly out of scope.

Tests: round-trip with/without the byte present (old-format fixture), default-false for pre-existing catalogs.
2. `optimizer.zig`: **real prerequisite, not polish** — add a "required referenced columns" collection pass (new function collecting `column_ref`s from `Project`/`Filter`/`Sort`/`Aggregate`/`Window`/`Join.on_condition` for a given table/alias, generalizing the existing `exprMentionsTable`-style walk at optimizer.zig:448-458) and feed its output into `indexCoversColumns` instead of the full table schema. Likely needs a small structural change to `Optimizer.optimize()` (precompute a `table/alias → []ColumnRef` map once, pass down) since the current recursive-descent shape gives leaf-level `optimizeScan` no ancestor context. Pure, storage-independent, unit-testable on constructed `PlanNode` trees; still a no-op end-to-end (nothing downstream reads `index_only` yet).

Inside the `.btree` branch, when `idx.covering_storage`, resolve `included_columns` → `vals[]` and call `index_entry.encodeIndexEntry` instead of the plain row_key dupe; unchanged when `!idx.covering_storage`. `deleteIndexEntries` needs no change (delete-by-key, value format irrelevant). Still no SQL-visible behavior change (`covering_storage` always false until step 4) — test via direct unit calls with a manually-constructed `covering_storage=true` `IndexInfo`.

## WAL Sender/Receiver Real I/O — Architect Design (Session TBD)

**Problem**: `src/replication/sender.zig`/`receiver.zig` (~1370 lines combined) plus 8000+ lines of protocol/slot/sync/monitor/backup/cascade/switchover/standby scaffolding are unit-tested but built on two literal no-op stubs: `WalReceiver.connect()` just sets `connected = true` (no TCP), `processWalData`/`flushWal`/`applyWal` only copy LSN counters around an in-memory buffer (no file write, no page replay); `WalSender.readWalChunk()` always returns 0 bytes regardless of `current_lsn`/`wal_end`, and `wal_file` is declared but never opened anywhere in the file. `protocol.zig`'s message types/encode-decode are real and usable as-is.

**Key findings from source review (not in the original task brief)**:
1. **Checkpoint truncates the WAL file** (`Wal.checkpoint`, wal.zig:308-371) — resets `total_frame_count`/salts and calls `file.setEndPos(0)`. `WalHeader.checkpoint_seq` already exists, apparently anticipating this. A naive "LSN = raw byte offset in the current WAL file" scheme is **not** globally monotonic across a checkpoint — offset 0 means a different point in history after every checkpoint. LSN must be `(checkpoint_seq, offset_within_epoch)`, not a bare file offset.

Sender/receiver must reuse this exact model, not invent async I/O.
3. **Existing sender/receiver unit tests feed arbitrary non-frame byte strings** through `processWalData`/`readWalChunk` and only assert LSN-counter bookkeeping — real frame parsing must be gated behind new `null`-by-default fields so this large existing test suite stays meaningful and green untouched.
4. `slot.zig`'s `SlotManager.getMinRestartLSN()` already exists — the missing piece for checkpoint/replication-retention coordination is on the `wal.zig` side, not `slot.zig`.

## Phase 6 — Checkpoint vs Replication Retention (Architect Design, session 542)

Full architect report follows (condensed). See git history / ask again if the full verbatim report is needed.

**Key finding beyond the original Phase 6 deferral note**: the "two incompatible LSN representations" concern turned out to already be solved, just undocumented — `sender.zig`/`receiver.zig` both have private `packLsn`/`unpackLsn` (`protocol.LSN (u64) = (checkpoint_seq << 32) | frame_index`), which round-trips correctly with `wal.Lsn.order()`. No wire-format change needed.

**Separate real bug found**: `WalSender.processStandbyStatus` (`sender.zig:158-166`) calls `updateSlotLSN(name, null, flush_lsn)` — `restart_lsn` param is always `null`, so `SlotManager`'s `restart_lsn` is stuck at its `0` init value forever in production, even for a fully caught-up active replica. `getMinRestartLSN()`'s only caller anywhere in the repo is its own test file — it is currently 100% dead/disconnected plumbing. Must fix before wiring checkpoint retention, else retention would either never trigger (0 read as "nothing ever safe to truncate" if checkpoint used it naively) or the reverse depending on comparison direction — either way meaningless.

**Design decisions**:
1. **LSN reconciliation**: keep `protocol.LSN = u64` as-is (already a packed `Lsn`). Promote `sender.zig`/`receiver.zig`'s duplicated private `packLsn`/`unpackLsn` into public `Lsn.pack()`/`Lsn.unpack(u64)` methods on `wal.Lsn` (single source of truth). Fix `protocol.zig`'s stale "byte offset" doc comment.
2. **Checkpoint behavior when replica lags**: **defer (skip) truncation, never refuse/error.** True partial truncation isn't feasible — `frameOffset(frame_index) = WAL_HEADER_SIZE + frame_index * frame_size` is checkpoint_seq-independent, so frame N of epoch K and epoch K+1 share the same byte range; truncation must stay whole-epoch. Split `checkpoint()`'s two jobs: flush (copy WAL pages → main DB file, always unconditional) vs reclaim (truncate + bump checkpoint_seq, conditional on `getMinRestartLSN() >= currentLsn()` for the epoch being discarded, else skip and retry next call). Accepted trade-off: primary WAL grows unboundedly while any slot is behind/orphaned — same well-known operational hazard as real Postgres abandoned replication slots; ops must monitor, not this plan's job to solve. `checkpoint()`'s only non-test caller (`engine.zig:1398`, `Database.close()`) already does `catch {}`, so an error-return design would be invisible there anyway.
3. **Wiring shape**: do NOT give `Wal` a `*SlotManager` field (wrong layering — storage importing replication). Instead `Wal` gets an optional callback: `min_retained_lsn_fn: ?*const fn(*anyopaque) ?u64 = null` + `min_retained_lsn_ctx: ?*anyopaque = null` + `setRetentionCallback(self, ctx, comptime f)`/`clearRetentionCallback`, `null` by default (zero behavior change for all existing non-replication callers/tests). `Database.wal` is already public — wiring point for a real `SlotManager` belongs in `server.zig`, but `server.zig` currently has **zero** `SlotManager` wiring at all (confirmed via grep) — scoped as optional/follow-up, not required for this plan.

**3-phase implementation plan**:
- **Phase 1** (`wal.zig`, `sender.zig`, `receiver.zig`, `protocol.zig`): `Lsn.pack`/`Lsn.unpack` public methods (dedupe from sender/receiver private copies); fix `processStandbyStatus` to pass `flush_lsn` for both restart_lsn and confirmed_flush_lsn (`updateSlotLSN(name, flush_lsn, flush_lsn)`); fix protocol.zig doc comment. Done when: regression test proves restart_lsn now advances (red before fix), pack/unpack round-trip test, order-preservation test (`a.order(b)` agrees with `a.pack() < b.pack()` as raw u64).
- **Phase 2** (`wal.zig` only, the core fix): add retention callback fields + `setRetentionCallback`; change `checkpoint()`'s early-return guard from `page_index.count() == 0` to `page_index.count() == 0 and committed_frame_count == 0` (so a later no-op-flush call can still retry deferred truncation); truncation-safety check — no callback set → truncate (back-compat default), callback returns null → truncate (no slots), callback returns min_lsn behind current → skip truncation entirely (file/counters untouched), caught up → truncate. Done when: existing checkpoint tests pass unmodified with no callback registered; new tests for defer-then-truncate-on-catch-up, WAL growth across multiple deferred rounds, and the actual regression proof (`readRawFrames()` against an old not-yet-truncated epoch still works while deferred).
- **Phase 3** (`slot.zig` trampoline + new integration test, style of `src/replication/integration_test.zig`): required — end-to-end test wiring a real `SlotManager` via `db.wal.?.setRetentionCallback`, simulating lagging-then-caught-up replica, asserting defer-then-truncate. Optional/follow-up, not required: give `Server` an owned `SlotManager` and wire `Server.init` (server.zig has zero replication wiring today, separate scoped work).

**Other flags from architect**: `packLsn`/`unpackLsn` duplication in sender.zig/receiver.zig is a DRY issue, worth cleaning up in phase 1. Once wired, a permanently-disconnected/never-streamed slot pins retention forever — mirrors real Postgres's "abandoned replication slot" pitfall; `monitor.zig` already tracks lag and could eventually alert on this, not this plan's job.

## MATCH_RECOGNIZE — Architect Design (Session TBD, 2026-09-02)

It is the single largest unimplemented SQL:2016 feature. **Scope decision (v1 — "reasonable honest subset", explicit per-feature include/defer list)**:

*Included*:
- `PARTITION BY expr, ...` and `ORDER BY expr, ...` (ORDER BY required — enforced by the analyzer, not the parser, matching this codebase's convention of parser-permissive/analyzer-strict for clause requirements).
- `MEASURES expr AS alias, ...`.
- `ONE ROW PER MATCH` (default) and `ALL ROWS PER MATCH` (basic form only — no `WITH UNMATCHED ROWS` / omit-vs-show-empty-matches nuance).
- `AFTER MATCH SKIP PAST LAST ROW` (default) and `AFTER MATCH SKIP TO NEXT ROW`.
- `PATTERN (...)`: concatenation (juxtaposition), alternation (`|`), grouping (`(...)`), greedy quantifiers `+` (one-or-more), `*` (zero-or-more), `?` (zero-or-one).
- `DEFINE var AS condition, ...` with navigation functions `PREV(expr [, n])`, `NEXT(expr [, n])`, `FIRST(expr [, n])`, `LAST(expr [, n])`, plus `MATCH_NUMBER()` and `CLASSIFIER()` usable in both `DEFINE` and `MEASURES`.
- Pattern variables referenced as `var.column` inside `DEFINE`/`MEASURES` (qualifier is a pattern variable, not a table alias — resolved specially by the analyzer, reusing the existing qualified `column_ref`/`Name` AST shape).

*Explicitly deferred (documented, not silently missing)*:
- `SUBSET` (union pattern variables), `PERMUTE(...)`, exclusion syntax `{- var -}`.
- Reluctant quantifiers (`+?`, `*?`, `??`) and bounded quantifiers (`{n}`, `{n,m}`, `{n,}`).
- Anchors `^`/`$` inside `PATTERN`.
- `AFTER MATCH SKIP TO FIRST var` / `SKIP TO LAST var` (only the two unconditional forms above ship in v1).
- `ALL ROWS PER MATCH WITH UNMATCHED ROWS` and empty-match handling (a pattern that can legally match zero rows, e.g. bare `A*`).
- Nested/lateral use inside a bigger single-table-only pipeline: v1 requires the MATCH_RECOGNIZE'd table reference to be a plain table, subquery, or table function (whatever `TableRef.source` already supports) but does **not** need to support it as a join operand with ON-condition interaction beyond normal FROM-item composition — no special-casing there, it's just another `TableRef`.
- Cost-based plan choices: like every other rule-based operator in this codebase (bitmap scan, GIN), there is no alternative physical strategy — one execution path, no optimizer cost comparison.

**Design decisions**:
1. **One new hard keyword**: `kw_match_recognize`, added exactly like `kw_row_number`/`kw_dense_rank` (single token, since `_` is already an identifier character) — collision risk with a real column/table named `match_recognize` is negligible, so this is safe to reserve outright (unlike `pattern`/`measures`/`define`, which are plausible existing column names).
2. **All inner clause words are soft/contextual keywords**, not tokenizer-reserved: `MEASURES`, `PATTERN`, `DEFINE`, `AFTER`, `MATCH`, `SKIP`, `PAST`, `NEXT`(reused, already `kw_next`? — verify at implementation time, else contextual), `ROW`(reused `kw_row`), `PER`, `ONE`. Checked via the exact `self.peek().type == .identifier and std.ascii.eqlIgnoreCase(...)` idiom already used for `first`/`last`/`ordinality`/`nulls`. `PARTITION`/`BY`/`ORDER`/`ROWS` reuse their existing real keywords (`kw_partition`/`kw_by`/`kw_order`/`kw_rows`) since those are already fully reserved SQL keywords in this codebase with no backward-compat concern.
3. **`PATTERN (...)` reuses existing tokens, contextually reinterpreted, via a dedicated sub-parser** scoped strictly to the token span between the `PATTERN` clause's matching parens: `.plus`→one-or-more, `.star`→zero-or-more, `.placeholder`(`?`)→zero-or-one, `.bitwise_or`→alternation, `.left_paren`/`.right_paren`→grouping, `.identifier`→pattern variable name. This is a parser-level (not tokenizer-level) reinterpretation, exactly analogous to how `-` is already contextually resolved as either subtraction or unary negation depending on parse position elsewhere in `parser.zig` — it does **not** create any new lexical ambiguity with bind-parameter `?` usage elsewhere in a query, since the sub-parser only ever runs inside the already-located `PATTERN ( ... )` span.
4. **New AST types in `ast.zig`** (grouped near `WindowFunctionExpr`/`WindowFrameSpec`):
   - `PatternQuantifier = enum { one_or_more, zero_or_more, zero_or_one }`
   - `PatternNode = union(enum) { variable: []const u8, concat: []const *const PatternNode, alternation: []const *const PatternNode, group: *const PatternNode, quantified: struct { node: *const PatternNode, quantifier: PatternQuantifier } }`
   - `DefineItem = struct { variable: []const u8, condition: *const Expr }`
   - `MeasureItem = struct { expr: *const Expr, alias: []const u8 }`
   - `RowsPerMatch = enum { one_row, all_rows }`
   - `AfterMatchSkip = enum { past_last_row, to_next_row }` (a plain enum suffices for v1's two unconditional forms; becomes a tagged union only if/when `to_first`/`to_last var` variants are added later)
   - `MatchRecognizeSpec = struct { partition_by: []const *const Expr = &.{}, order_by: []const OrderByItem = &.{}, measures: []const MeasureItem = &.{}, rows_per_match: RowsPerMatch = .one_row, after_match_skip: AfterMatchSkip = .past_last_row, pattern: *const PatternNode, define: []const DefineItem = &.{} }`
   - `TableRef` gains a 5th variant: `match_recognize: struct { source: *const TableRef, spec: MatchRecognizeSpec, alias: ?[]const u8 = null }` — wraps an inner `TableRef` (itself `table_name`/`subquery`/`table_function`/`values_table`, or even another `match_recognize` — not disallowed, just untested/unneeded in v1), matching the "modifier wraps a `TableRef`" shape subqueries already use rather than becoming a new top-level AST node.
5. **`PREV`/`NEXT`/`FIRST`/`LAST`/`MATCH_NUMBER`/`CLASSIFIER` are plain `Expr.function_call` nodes**, not new `Expr` variants — their syntax (`NAME(args...)`) fits `function_call` exactly, unlike `window_function`/`ordered_set_agg` which needed dedicated variants because of extra non-function-call clauses (`OVER (...)`, `WITHIN GROUP (...)`). The analyzer/executor recognize them by name only within `DEFINE`/`MEASURES` evaluation context, the same way `evalExpr` already special-cases other builtin function names elsewhere in `executor.zig`.
6. **Executor pattern-matching core lives in a new standalone module `src/sql/pattern_match.zig`**, independent of `Row`/`Value`/`Database` — operates purely over `(row_count: usize, matches_predicate: fn(variable: []const u8, row_idx: usize, tentative_bindings: ...) bool)` via a small caller-supplied interface, so it is unit-testable with fake predicates and no executor/DB plumbing at all. This mirrors the `src/sql/bitmap.zig` (`RowKeySet`) precedent of factoring a pure, storage-independent algorithm into its own file rather than burying it inside `executor.zig`. It implements a backtracking matcher over the compiled `PatternNode` tree (NFA-style greedy backtracking is sufficient at v1's scope — no reluctant quantifiers, no bounded repetition — so a plain recursive backtracker, not a full Thompson-NFA construction, is the right level of engineering for what's in scope; revisit only if reluctant/bounded quantifiers are ever added).
7. **`MatchRecognizeOp` in `executor.zig`** is `WindowOp`'s structural twin: buffers all input rows, sorts by `spec.partition_by ++ spec.order_by` (reusing `WindowOp`'s existing `WindowSortContext`/`samePartition` helpers verbatim rather than duplicating them — may require lifting them from `WindowOp`-private to file-private visibility), walks partition boundaries, and within each partition repeatedly invokes `pattern_match.zig`'s matcher starting at each unconsumed row (advancing past a match per `after_match_skip`, or by one row on no-match) to produce a list of matches (each a `{start, end, variable_per_row: []const []const u8}`). For each match, evaluates `MEASURES` expressions (with `PREV`/`NEXT`/`FIRST`/`LAST`/`MATCH_NUMBER`/`CLASSIFIER` resolved against the match's row range) to build output row(s) per `rows_per_match`.
